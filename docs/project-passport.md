# Паспорт проекта Harbor Transfer Portal

> Короткое описание продукта для операторов, администраторов, руководителей и других пользователей, которым важно понять назначение Portal без изучения исходного кода и DevOps-инструментов.

## Что это за продукт

**Harbor Transfer Portal** — локальный веб-портал для безопасной офлайн-передачи container images и Helm OCI charts между сетево изолированными Harbor-контурами.

Простыми словами: если две площадки не имеют прямого сетевого соединения, Portal помогает подготовить артефакты на одной стороне, перенести их на разрешённом физическом носителе и проверить перед загрузкой на другой стороне.

Оператору для штатного переноса не требуется вручную работать с `skopeo`, `helm`, `tar`, `sha256sum` или Harbor CLI.

## Для какой проблемы он нужен

Обычная репликация Harbor предполагает сетевую доступность между registry. В данном проекте это запрещённое предположение: SOURCE и TARGET работают в независимых изолированных контурах и не соединяются напрямую.

Portal заменяет ручную цепочку команд управляемым процессом:

```text
Harbor SOURCE
    ↓
Harbor Transfer Portal в SOURCE role
    ↓
подписанный offline bundle
    ↓
разрешённый физический носитель
    ↓
Harbor Transfer Portal в TARGET role
    ↓
проверка и импорт
    ↓
Harbor TARGET
```

## Кто пользуется порталом

### Оператор

Основной пользователь. Выбирает артефакты, запускает export/import, следит за результатом операции и использует историю/отчёты.

### Администратор

Настраивает локальные Harbor profiles, пользователей, политики передачи, ключи подписи/доверия и эксплуатационные параметры Portal.

### Наблюдатель

Имеет доступ только на чтение к разрешённой информации, например истории и результатам операций. Не запускает передачу и не меняет настройки.

## SOURCE и TARGET — в чём разница

Один и тот же software/deployment поддерживает две runtime roles. В production air-gap физически раздельные контуры обычно имеют собственные установки Portal.

| Runtime role | Назначение | Основное действие |
|---|---|---|
| **SOURCE** | Подготовить артефакты к переносу | Создать и скачать offline bundle |
| **TARGET** | Проверить полученный пакет и импортировать его | Принять, проверить и импортировать bundle |

Каждая установка работает только с Harbor endpoints своего локального контура. В одной установке может быть несколько именованных Harbor profiles, но SOURCE не хранит учётные данные TARGET, а TARGET не хранит учётные данные SOURCE.

## Типовой сценарий для оператора

### 1. На стороне SOURCE

1. Войти в Portal.
2. Убедиться, что текущая runtime role — **SOURCE**.
3. Выбрать SOURCE Harbor profile.
4. Выбрать нужные container images и/или Helm OCI charts из выбранного локального Harbor.
5. Проверить состав будущей поставки, версии и digest.
6. Запустить export.
7. Дождаться успешного завершения.
8. Скачать **три файла одной delivery**: `*.htp.tar.gz`, соответствующий `*.sha256` и signed `*.htp-handoff.json`.

### 2. Физический перенос

Скопировать **delivery triplet** — archive, `.sha256` и signed `.htp-handoff.json` — вместе на разрешённый носитель и перенести их в TARGET-контур по действующей организационной процедуре. Не переименовывайте и не редактируйте файлы по отдельности.

Portal не управляет физическим носителем и не заменяет правила информационной безопасности организации.

### 3. На стороне TARGET

1. Войти в Portal.
2. Убедиться, что текущая runtime role — **TARGET**.
3. Выбрать TARGET Harbor profile.
4. Передать Portal все три файла полученной delivery.
5. Дождаться проверки signed handoff, checksum, структуры/canonical manifest и Ed25519 signature Bundle v1.
6. Просмотреть состав пакета и состояния `NEW`, `SAME`, `CONFLICT`, `UNKNOWN`, `ERROR`.
7. Запустить разрешённый import.
8. Проверить итоговый результат, receipt, History и при необходимости скачать отчёт.

Полный browser-only workflow описан в [user-guide.md](user-guide.md).

## Что переносится

В v1.0.0 поддерживаются два основных типа артефактов:

- **container images** из Harbor;
- **Helm OCI charts** из Harbor.

Пакет передачи является не произвольным архивом, а версионированным форматом доставки со служебным manifest, контрольными суммами и электронной подписью.

## Как Portal защищает передачу

Безопасность строится из нескольких независимых проверок.

### Подпись

SOURCE подписывает manifest пакета. TARGET доверяет только заранее настроенным открытым ключам SOURCE. Подпись нужна для проверки происхождения и подлинности данных.

### Контрольные суммы

SHA-256 используется для обнаружения повреждения или изменения содержимого пакета.

Контрольная сумма сама по себе не доказывает, кто создал пакет, поэтому она не заменяет электронную подпись.

### Проверка структуры пакета

Перед импортом TARGET проверяет структуру и допустимость содержимого архива. Потенциально опасные пути и специальные типы файлов отклоняются до безопасной рабочей распаковки.

### Безопасная политика конфликтов

Если в TARGET уже существует тот же tag/version с другим содержимым, это считается **CONFLICT**. Перезапись по умолчанию не происходит автоматически.

`UNKNOWN` и `ERROR` также не считаются `NEW` и блокируют mutation до выяснения состояния.

## Какие результаты может увидеть пользователь

Операции имеют явные persisted states. В интерфейсе пользователь получает понятный итог, например:

- операция выполняется;
- пакет успешно создан;
- пакет проверен и готов к импорту;
- артефакт уже существует с тем же digest и безопасно пропущен;
- найден конфликт;
- пакет отклонён при проверке;
- операция завершилась ошибкой или была отменена.

Текстовый log не является источником истины для пользовательского результата: состояние и история операции хранятся структурированно.

## Что Portal принципиально не делает

- не создаёт сетевой канал между SOURCE и TARGET;
- не использует прямую Harbor-to-Harbor replication через границу изоляции;
- не хранит credentials противоположного контура;
- не отключает TLS verification незаметно для администратора;
- не заменяет signature одной только SHA-256 checksum;
- не перезаписывает конфликтующий artifact автоматически;
- не заменяет организационные правила обращения с физическими носителями;
- не делает непроверенный, отменённый или частично созданный bundle «успешной поставкой».

## Текущее состояние v1.0.0

Функциональный объём **v1.0.0 реализован и прошёл release qualification**. Завершены пользовательский/административный комплект документации, offline installation kit, clean-host qualification и isolated SOURCE → physical bundle → TARGET acceptance.

Это означает, что репозиторий содержит проверяемый release workflow, но не отменяет локальные эксплуатационные процедуры. Production rollout конкретной организации всё равно требует:

- локального change/release approval;
- проверки поддерживаемой инфраструктуры и storage;
- безопасной настройки Harbor credentials и private CA;
- provisioning SOURCE signing identity и TARGET trusted public keys;
- проверки backup/restore и организационного порядка физического переноса.

Release identity и ограничения текущей версии описаны в [release-notes-v1.0.0.md](release-notes-v1.0.0.md).

## Мини-словарь

| Термин | Простое объяснение |
|---|---|
| **Harbor** | Локальное хранилище container images и OCI-артефактов |
| **SOURCE** | Runtime role, в которой артефакты подготавливаются к вывозу |
| **TARGET** | Runtime role, в которой полученный bundle проверяется и импортируется |
| **Bundle / пакет** | Файл поставки с артефактами и данными для их проверки |
| **Digest** | Криптографический идентификатор содержимого OCI-артефакта |
| **SHA-256** | Контрольная сумма для проверки целостности |
| **Подпись** | Проверка того, что manifest создан доверенным SOURCE |
| **CONFLICT** | В TARGET есть та же ссылка/версия, но с другим содержимым |
| **Receipt** | Зафиксированный результат приёма/импорта поставки |
