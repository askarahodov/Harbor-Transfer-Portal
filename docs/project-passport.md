# Паспорт проекта Harbor Transfer Portal

> Короткое описание проекта для операторов, руководителей и других пользователей, которым важно понять назначение портала без изучения исходного кода и DevOps-инструментов.

## Что это за продукт

**Harbor Transfer Portal** — локальный веб-портал для безопасной офлайн-передачи контейнерных образов и Helm OCI-чартов между двумя сетево изолированными контурами.

Простыми словами: если две площадки не имеют прямого сетевого соединения, портал помогает подготовить артефакты на одной стороне, перенести их на разрешённом физическом носителе и проверить перед загрузкой на другой стороне.

Оператору не требуется вручную работать с `skopeo`, `helm`, `tar`, `sha256sum` или Harbor CLI.

## Для какой проблемы он нужен

Обычная репликация Harbor предполагает сетевую доступность между registry. В данном проекте это запрещённое предположение: SOURCE и TARGET работают в независимых изолированных контурах и не соединяются напрямую.

Портал заменяет ручную цепочку команд управляемым процессом:

```text
Harbor SOURCE
    ↓
Harbor Transfer Portal SOURCE
    ↓
подписанный офлайн-пакет
    ↓
разрешённый физический носитель
    ↓
Harbor Transfer Portal TARGET
    ↓
проверка и импорт
    ↓
Harbor TARGET
```

## Кто пользуется порталом

### Оператор

Основной пользователь. Выбирает артефакты, запускает экспорт или импорт, следит за результатом операции и использует историю/отчёты.

### Администратор

Настраивает локальный Harbor, пользователей, политики передачи, ключи подписи/доверия и эксплуатационные параметры портала.

### Наблюдатель

Имеет доступ только на чтение к разрешённой информации, например истории и результатам операций. Не должен запускать передачу или менять настройки.

## SOURCE и TARGET — в чём разница

Один и тот же продукт устанавливается отдельно в каждом контуре.

| Контур | Назначение | Основное действие |
|---|---|---|
| **SOURCE** | Подготовить артефакты к переносу | Создать и скачать офлайн-пакет |
| **TARGET** | Проверить полученный пакет и импортировать его | Принять и проверить пакет |

Каждая установка знает только свой локальный Harbor. SOURCE не хранит учётные данные TARGET, а TARGET не хранит учётные данные SOURCE.

## Типовой сценарий для оператора

### 1. На стороне SOURCE

1. Войти в портал.
2. Убедиться, что открыт контур **SOURCE**.
3. Выбрать нужные container images и/или Helm OCI charts из локального Harbor.
4. Проверить состав будущей поставки.
5. Запустить экспорт.
6. Дождаться успешного завершения.
7. Получить готовый пакет и контрольную информацию о нём.

### 2. Физический перенос

Скопировать подготовленный пакет на разрешённый носитель и перенести его в TARGET-контур по действующей организационной процедуре.

Портал не управляет физическим носителем и не заменяет правила информационной безопасности организации.

### 3. На стороне TARGET

1. Войти в портал.
2. Убедиться, что открыт контур **TARGET**.
3. Передать порталу полученный пакет.
4. Дождаться проверки структуры, подписи и контрольных сумм.
5. Просмотреть состав пакета и возможные конфликты.
6. Запустить импорт.
7. Проверить итоговый результат и историю операции.

## Что переносится

В рамках версии v1 проект рассчитан на два основных типа артефактов:

- **контейнерные образы** из Harbor;
- **Helm OCI-чарты** из Harbor.

Пакет передачи является не произвольным архивом, а версионированным форматом доставки со служебным manifest, контрольными суммами и электронной подписью.

## Как портал защищает передачу

Безопасность строится из нескольких независимых проверок.

### Подпись

SOURCE подписывает manifest пакета. TARGET доверяет только заранее настроенным открытым ключам SOURCE. Подпись нужна для проверки происхождения и подлинности данных.

### Контрольные суммы

SHA-256 используется для обнаружения повреждения или изменения содержимого пакета.

Контрольная сумма сама по себе не доказывает, кто создал пакет, поэтому она не заменяет электронную подпись.

### Проверка структуры пакета

Перед импортом TARGET проверяет структуру и допустимость содержимого архива. Потенциально опасные пути и специальные типы файлов должны быть отклонены до распаковки в рабочую область.

### Безопасная политика конфликтов

Если в TARGET уже существует тот же тег или версия с другим содержимым, это считается **CONFLICT**. Перезапись по умолчанию не должна происходить автоматически.

## Какие результаты может увидеть пользователь

Операции имеют явные состояния. В интерфейсе пользователь должен получать понятный итог, например:

- операция выполняется;
- пакет успешно создан;
- пакет проверен и готов к импорту;
- артефакт уже существует с тем же digest и безопасно пропущен;
- найден конфликт;
- пакет отклонён при проверке;
- операция завершилась ошибкой или была отменена.

Технический лог не является источником истины для пользователя: итог операции должен храниться как структурированное состояние и история.

## Что портал принципиально не делает

- не создаёт сетевой канал между SOURCE и TARGET;
- не использует прямую Harbor-to-Harbor репликацию через границу изоляции;
- не хранит учётные данные противоположного контура;
- не должен отключать TLS-проверку незаметно для администратора;
- не должен автоматически перезаписывать конфликтующий артефакт;
- не заменяет организационные правила обращения с физическими носителями;
- не делает непроверенный или частично созданный пакет «успешной поставкой».

## Что важно понимать перед эксплуатацией

Harbor Transfer Portal сейчас развивается как **v1**. Репозиторий уже содержит архитектурную, протокольную, security- и deployment-документацию, но полный пользовательский комплект и финальный offline release kit ещё входят в открытый план работ (#27 и #28).

Поэтому этот паспорт описывает назначение, обязательную модель работы и целевой пользовательский процесс. Для production-ввода необходимо использовать только подтверждённый релиз и пройти release/acceptance-проверки, а не считать текущую ветку разработки готовым поставочным комплектом.

## Мини-словарь

| Термин | Простое объяснение |
|---|---|
| **Harbor** | Локальное хранилище container images и OCI-артефактов |
| **SOURCE** | Контур, откуда артефакты вывозятся |
| **TARGET** | Контур, куда артефакты импортируются |
| **Bundle / пакет** | Файл поставки с артефактами и данными для их проверки |
| **Digest** | Криптографический идентификатор содержимого OCI-артефакта |
| **SHA-256** | Контрольная сумма для проверки целостности |
| **Подпись** | Проверка того, что manifest создан доверенным SOURCE |
| **CONFLICT** | В TARGET есть та же ссылка/версия, но с другим содержимым |
| **Receipt** | Зафиксированный результат приёма/импорта поставки |
