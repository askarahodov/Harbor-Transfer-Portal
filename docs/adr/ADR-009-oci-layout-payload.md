# ADR-009: OCI image-layout внутри офлайн-пакета

## Статус

Принято для Bundle Protocol v1.

## Контекст

Портал должен переносить контейнерные образы, включая multi-architecture indexes, через air-gap с сохранением проверяемой OCI-идентичности. Сам транспортный пакет уже является архивом `.tar.gz`, поэтому внутреннему представлению образа не требуется быть ещё одним Docker-style tar archive.

## Решение

Использовать каталог OCI image-layout как представление payload контейнерного образа. Сервисы экспорта и импорта используют OCI transport Skopeo и при необходимости сохраняют все manifests/platforms.

## Причины

- OCI layout напрямую сохраняет indexes, manifests, blobs и содержимое, адресуемое по digest.
- Формат подходит для multi-architecture содержимого, когда Skopeo копирует все manifests.
- Digest можно проверять по OCI metadata, а не выводить идентичность из имён файлов внутри tar.
- Внешний `.htp.tar.gz` уже обеспечивает физическую переносимость одним файлом.
- Каталожный payload позволяет явно рассчитывать checksum для каждого файла и строго валидировать безопасную распаковку архива.

## Отклонённый вариант

`docker-archive:` и другие представления single-image tar не выбраны, поскольку они хуже соответствуют OCI indexes и требованиям сохранения multi-arch.

`oci-archive:` остаётся возможной будущей оптимизацией transport-уровня, но v1 использует каталожную форму, чтобы структура и процедура проверки оставались явными.

## Последствия

Verifier пакета обязан:

- проверять checksum всех файлов OCI layout;
- разрешать только безопасные относительные пути;
- после импорта независимо проверять итоговый артефакт в TARGET Harbor.

Успешный код завершения Skopeo сам по себе не является доказательством успешной доставки.
