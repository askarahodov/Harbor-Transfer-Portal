# Безопасность локального входа

## Обзор

Backend ограничивает неуспешные попытки входа, чтобы снизить риск brute-force атак. Ограничения применяются одновременно по имени пользователя и адресу клиента.

## Пороги по умолчанию

| Параметр | Значение | Описание |
|---|---|---|
| `LOGIN_RATE_LIMIT_WINDOW_SECONDS` | 300 | Окно подсчёта ошибок |
| `LOGIN_RATE_LIMIT_USERNAME_MAX_FAILURES` | 5 | Максимум ошибок для одного username |
| `LOGIN_RATE_LIMIT_ADDRESS_MAX_FAILURES` | 20 | Максимум ошибок для одного client address |
| `LOGIN_RATE_LIMIT_LOCKOUT_SECONDS` | 900 | Блокировка после достижения порога |

Адресный порог выше пользовательского, чтобы снизить риск блок нескольких операторов за общим reverse proxy.

## Хранение состояния

Счётчики хранятся в SQLite, поэтому сохраняются при обычном рестарте приложения. В таблицу `login_throttles` не записываются исходные username и client address — вместо них используется HMAC-SHA256 отпечаток на ключе установки `JWT_SECRET`.

## Поведение

- Успешный вход очищает счётчик конкретного username.
- Адресный счётчик сбрасывается естественно после окна.
- Заблокированные и обычные неверные попытки возвращают одинаковую ошибку `invalid credentials` — механизм не должен использоваться как признак существования учётной записи.

## Настройка

Параметры можно изменить через окружение:

```bash
LOGIN_RATE_LIMIT_WINDOW_SECONDS=300
LOGIN_RATE_LIMIT_USERNAME_MAX_FAILURES=5
LOGIN_RATE_LIMIT_ADDRESS_MAX_FAILURES=20
LOGIN_RATE_LIMIT_LOCKOUT_SECONDS=900
```

**Важно:** не устанавливайте слишком низкий адресный порог без анализа схемы reverse proxy. Приложение намеренно не доверяет произвольному пользовательскому `X-Forwarded-For` само по себе.

## API-эндпоинты

- `POST /api/auth/login` — вход; возвращает `access_token` или `401 invalid credentials`
- `GET /api/auth/me` — текущий пользователь (требует токена)
